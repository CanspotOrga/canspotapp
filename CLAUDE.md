# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static HTML prototype for **CanSpot** (`<title>`: "CanSpot"), a German-language mobile-first price-comparison app for energy drinks. There is no build step for the web app. `index.html` contains all CSS, inline SVG icons, and JavaScript in one file; it loads all data live from Supabase (see [Datenquelle (Supabase)](#datenquelle-supabase)).

## Running / previewing

No build or install step — open the HTML file directly, or serve it locally. A dev server config already exists at `.claude/launch.json`:

```bash
python3 -m http.server 8123
```

(matches the `canspot-preview` launch config, serving the current directory on port 8123). There is no lint, test, or build command — this is plain HTML/CSS/JS with no tooling configured.

## Architecture

Everything lives in one file, in this order: `<style>` (CSS custom properties + component styles) → SVG `<symbol>` icon sprite → `<body>` markup (app shell, sheets/modals) → one `<script>` block with all logic (data is loaded from Supabase at runtime).

**Theming**: CSS custom properties are defined on `:root` (light) and overridden under `:root[data-theme="dark"]`. Theme resolution (`light`/`dark`/`system`, from `localStorage["canspot-theme"]`) happens twice: once in a tiny inline `<script>` in `<head>` (sets `data-theme` before first paint to avoid a flash of the wrong theme) and again later via `applyTheme()` once the UI is interactive.

**Data model** (top of the main `<script>`) — `products`, `storeLogos`, `storeBranches`, and `deals` are declared as empty `let` placeholders and populated at runtime by `loadDeals()` from **Supabase** (see [Datenquelle (Supabase)](#datenquelle-supabase) below). There is no demo/fallback data anywhere in the app.
- `products` — catalog (id, name, brand, sizeMl, optional image URL, isNew, packaging) from `public.products` + `brands`.
- `storeLogos` / `storeBranches` — retailer logo URL and branch info (address, hours, geo) from `public.retailers` + `branches`, keyed by retailer name (first branch per retailer wins).
- `deals` — runtime array: `public.offers` joined with product info via `buildDeals()`, plus `totalMl` (`sizeMl × units`), `priceHistoryPoints` (only real `public.price_history` rows — empty if none, never synthesized), a derived `history` array, and `lastCheckedAt` (`offers.last_checked_at`, `null` if missing).
- `TODAY` is the real current date (local midnight) — all "days until expiry / week grouping" logic (`daysUntil`, `weekIndexOf`) is relative to it. Expired offers are hidden by default (`hideExpired`); when shown, they are grouped under "Abgelaufen".
- Nutrition (`NUTRITION_BY_PRODUCT` / `NUTRITION_BY_BRAND`) and rating aggregates (`productRatingSummaries`, via RPC `get_all_product_rating_summaries()`) are filled from Supabase only; missing values render as "Keine Nährwertangaben vorhanden." / "–".

**State & rendering**: No framework — plain module-level `let` variables (`selectedBrand`, `favorites` (a `Set`), `radiusKm`, `viewMode`, `hideExpired`, etc.) hold UI state, mutated by event listeners attached directly via `addEventListener`/`querySelectorAll`. Each state change is followed by an explicit call to the relevant render function:
- `render()` — filters + sorts `deals`, rebuilds the `#deals` list (or shows an empty state), and also triggers `renderMap()`. The list is additionally grouped into purely visual "Angebotszeitraum" sections: `weekIndexOf(dateStr)` buckets a date into a Monday-based week offset from `TODAY` (0 = current week, 1 = next week, etc.), deals are grouped by `weekIndexOf(deal.validUntil)` while preserving the current sort's relative order within each group (a stable partition, not a re-sort), and `periodGroupLabel(weekIndex)` turns the bucket into "Abgelaufen" (all past weeks, bucket -1) / "Diese Woche" / "Nächste Woche" / "In N Wochen" — extensible to further weeks without new hardcoded labels. Each week renders as two always-adjacent siblings in `#deals`: a `.period-header` (title, date range, and the expand/collapse toggle) followed by a `.period-group` wrapping a `.period-group-inner` that holds that week's `.card`s (cards themselves are built by `buildDealCardEl()` and stay untouched). Each header's date range is `formatDateRange(minValidFrom, maxValidUntil)` computed from the deals actually in that group (not an independently-computed calendar week), and a group is only rendered if it has at least one deal. Map view and the empty state are unaffected (grouping only applies to the non-empty list-view render path).
  - **Accordion toggle**: `.period-header`s stay visible at all times (so every week stays reachable); only each week's `.period-group` collapses/expands, and each week's open/closed state is fully independent of every other week's (collapsing or expanding one week never affects any other week's cards — there is no single-open-accordion/isolation behavior here). The header's `.period-toggle` button (chevron icon + "N Angebote" count, `data-period-toggle="<weekIndex>"`) is the click target — a delegated listener on `dealsContainer` adds/removes that week's index from module-level `collapsedPeriodWeeks` (a `Set`; empty = every group expanded, the default/resting state — a week index present in the set means only that week's `.period-group` gets `.collapsed`). `[aria-expanded]` on the button drives both the chevron's 180° rotation (CSS `transform`, `.period-chevron`) and screen-reader state. The expand/collapse animation itself is a CSS Grid `grid-template-rows: 1fr` ↔ `0fr` transition on `.period-group` (with `.period-group-inner{overflow:hidden}` clipping the content) rather than a `max-height` transition — chosen deliberately because it animates to the content's true intrinsic size regardless of magnitude, which matters here since week groups vary hugely in size (e.g. 1 vs. 60 deals) and a fixed `max-height` ceiling large enough for the biggest group would make small groups' animations look instant/mistimed. This toggle is independent of the "Filter"-sheet's own `periodFilter` (different variable, different concept — "Läuft bald ab"/"Neu" on `validFrom`/`validUntil` windows, not week buckets). If a collapsed week has no deals left after some other filter/sort change, its now-unused entry simply stays harmlessly in `collapsedPeriodWeeks` (never rendered, never re-read) rather than needing explicit cleanup.
- `renderMap()` — draws the radial "map" view (store pins positioned by hashed angle + normalized distance, not real coordinates).
- `renderAlertsView()` — the "Alarme" tab (price-alert cards + computed favorite events).
- Views (list/map/alerts, and the profile/history/store-detail/location/filter/sort sheets) are all plain DOM containers shown/hidden — there is no router.
- **Bottom navigation** (`nav.bottomnav`, 5 tabs: Start/Neuheiten/Favoriten/Alarme/Mein Bereich): Start, Neuheiten, and Favoriten all render into the *same* `#deals` list via `render()` — each just sets its own independent boolean filter flag (`viewFavoritesOnly`, `viewNewOnly`) before calling `showDealsView()`, rather than being separate pages/templates. Only Alarme (`#alertsView`) and Mein Bereich (a sheet) are genuinely separate containers. `viewNewOnly` filters `deals` down to `deal.isNew` (from `products[].isNew`, see above) — deliberately its own variable rather than reusing the pre-existing `sort.value==="new"` option (a single global, also directly selectable from the sort sheet; piggybacking the nav tab on it would leak the restriction into Favoriten/Home after switching tabs, since those don't reset `sort.value`). Each nav handler that can turn one of these flags on is responsible for turning the *other* one off (e.g. `navFav` sets `viewNewOnly = false`) — `navAlerts`/`navProfile` don't touch either flag, matching how they already left `viewFavoritesOnly` alone.

**Nur mobile Ansicht**: Es gibt keine eigene Web-/Desktop-Variante mehr. Alle früheren `@media (max-width:540px)`-Blöcke sind `@media all{…}` (gelten immer), und `isMobileMapViewport()` liefert immer `true` (echte Leaflet-Karte überall). Im breiten Browserfenster erscheint dieselbe Handy-Ansicht, zentriert in der 560px breiten `.app`-Spalte. Neue Regeln nicht wieder an eine Bildschirmbreite koppeln. Die älteren Desktop-Zweige (z. B. alte radiale Kartenansicht, `#notifBtn`-Glocke) sind dadurch toter Code und können aufgeräumt werden.

**iOS (`www/`)**: `www/` ist die Capacitor-Kopie von `index.html`, `service-worker.js`, `manifest.webmanifest`, `icons/`, `lib/`. Nach Änderungen dorthin kopieren und `npx cap copy ios` ausführen (füllt das git-ignorierte `ios/App/App/public`).

**Sheets/modals**: bottom-sheet overlays (`.overlay` + `.sheet`) are generic — `openSheet(id)` / `closeSheet(id)` toggle the `.open` class on any `#...Overlay` element. New sheets should follow the existing markup pattern (`.overlay > .sheet > .sheet-inner`, optional `.sheet-scroll` + `.sheet-footer` for tall/scrolling sheets).

**Persistence**: `localStorage` only, no server sync. Keys in use: `canspot-theme`, `canspot-alerts`, `canspot-firstname`, `canspot-lastname`, `canspot-email`, `canspot-birthdate`, `canspot-address`, `canspot-avatar`, `canspot-notif-*`, `canspot-ratings`.

**Images**: `products.image_url`, `retailers.logo_url` and `offers.bundle_image_url` are optional and currently empty. When a value is missing, `onerror`/fallback handlers render inline SVG data-URIs (`FALLBACK_IMG`, `STORE_FALLBACK_IMG`). Only fill these columns with images allowed by [DATENQUELLEN.md](DATENQUELLEN.md) (Open Food Facts with attribution, own photos, or written permission) — never hotlink or copy images or logos from retailer or manufacturer websites. `buildDeals()` prefers `offer.bundleImg` (multipack image) over `product.img` when present.

**Init sequence**: `loadDeals()` (at the very end of the script) calls `renderSkeleton(4)`, then awaits `Promise.all([loadFromSupabase(), delay(500)])` (500ms floor so the skeleton doesn't just flash). On success it fills the data via `applyLoadedData()` and calls `finishInit()`; an empty database is not an error (normal "Keine Angebote gefunden" state). On a network/database error in a core table (products/branches/offers) it calls `showLoadError()` with an "Erneut versuchen" button wired back to `loadDeals()`. Content is not present until Supabase answers.

## Datenquellen: rechtliche Regeln (verbindlich)

Before adding, importing or linking any product, price, store, image or logo data, read [DATENQUELLEN.md](DATENQUELLEN.md). It overrides every other note in this file. In short: never pull data, images or logos from retailer websites or apps (REWE, EDEKA, Kaufland, Lidl, ALDI, Netto, …) by any means, including a driven browser; bot protection means stop; allowed without an agreement are only OpenStreetMap, Open Food Facts (with attribution), own/user-reported data and clearly labelled made-up demo data.

## Datenquelle (Supabase)

All data comes live from the Supabase project configured at the top of the script (`SUPABASE_URL` + publishable key; never put a secret/service_role key in client code). There is no local fallback data in the app. The database state is mirrored in the repo under `supabase/` (see `supabase/README.md`): `schema.sql` (tables, RLS, grants, functions), `seed.sql` (current content rows, idempotent), `reset_inhalte.sql` (empties content tables) and `data/*.csv`. When you change the live database, update these files in the same change, and vice versa. `supabase/seed/` stays local-only (git-ignored) and must never be committed.

- Core tables (a load error here → `showLoadError()`): `products` (+`brands`), `branches` (+`retailers`), `offers`.
- Optional (an error only hides that info): `product_nutrition`, `brand_nutrition_defaults`, `price_history`, RPC `get_all_product_rating_summaries()`.
- `branches.opens_at/closes_at` (SQL `time`) are converted to float hours for `isStoreOpenNow()`; the open/closed status is always computed client-side, never stored.
- `distanceKm` is not stored; it's computed from branch coordinates (initially against `DEFAULT_LOCATION_GEO`, then the real GPS position via `applyRealDistances()`).

## Progressive Web App (PWA)

The app is installable and works offline. This adds a few files alongside `index.html`, all wired with **relative** paths (no leading `/`) so it keeps working when served from a GitHub Pages project subpath (`https://<user>.github.io/<repo>/`), not just the domain root:

- `manifest.webmanifest` — name "CanSpot", `theme_color`/`background_color` matching the app's dark palette, `start_url`/`scope` set to `./`, and icon entries (see below).
- `icons/` — generated PNGs: `favicon-16.png`, `favicon-32.png`, `icon-192.png`, `icon-512.png` (purpose `any`), `icon-maskable-512.png` (purpose `maskable`, extra padding for Android's adaptive-icon safe zone), `apple-touch-icon-180.png`. All share the same mark — the can/location-pin glyph isolated from the logo SVG's standalone icon paths (i.e. the three `<path>` elements outside the lettering `<g>` in the header logo), white/`--brand-primary-blue` on a flat `--brand-primary-dark` background, rounded-square corners on every size except `icon-maskable-512` (full-bleed square; the OS applies its own mask) — matches the app's `theme-color`. Regenerated via a canvas-drawing script (`new Image()` from a data-URI SVG of just those 3 paths, drawn onto a `<canvas>` per size/corner-radius/mark-scale, exported with `toDataURL`) — there's no source vector file or generator script checked in, so redo this the same way if the mark changes again.
- `service-worker.js` — cache-first for same-origin requests, precaches the app shell (`index.html`, the manifest, the icons and `lib/`) on install, and falls back to the cached `index.html` for navigation requests when offline. It does **not** cache external images (other origins). Supabase requests are cross-origin and therefore never cached — the app always shows live data.
- In `index.html`'s `<head>`: `<link rel="manifest">`, favicon `<link>`s, `apple-touch-icon`, and the `apple-mobile-web-app-*` / `mobile-web-app-capable` meta tags for iOS/Android homescreen install. The service worker is registered at the very end of the main `<script>` block (after `loadDeals()` is kicked off), gated on `"serviceWorker" in navigator`, so it doesn't affect the existing init sequence or any UI behavior.
- **Mandatory cache-bump rule (no reminder needed):** `APP_SHELL` in `service-worker.js` lists every file the service worker precaches and serves cache-first (`index.html`, `manifest.webmanifest`, all `icons/*.png`, `lib/*`). Whenever a change touches the *content* of one of these files — including any edit inside `index.html`'s inline `<style>`, `<script>`, or markup, since it's the single-file app shell — bump `CACHE_NAME` in `service-worker.js` (currently `canspot-cache-v154`; next bump would be `v155`) as part of that same change, automatically, without being asked. The `activate` handler deletes old-named caches on its own once the version string changes. Without the bump, a returning visitor or already-installed PWA keeps being served the old cached files indefinitely — a `git push` updates GitHub Pages, but the change stays invisible on the live/test site until the cache is forced to invalidate. Only skip the bump for changes that touch nothing in `APP_SHELL` (e.g. only `PROJECT_STATE.md`, `CLAUDE.md` or files under `supabase/`).

## Workflow: progress log & commits

Before treating any change as finished: check whether it touched a file listed in `service-worker.js`'s `APP_SHELL` (see **Progressive Web App (PWA)** above — in practice this means almost any `index.html` edit). If so, bump `CACHE_NAME` in the same change, so that a normal `git commit` + `git push` reliably updates the live GitHub Pages/test site instead of leaving visitors on a stale cached version. This applies automatically, every time, without the user needing to ask for it.

After every completed change, add a short entry to [PROJECT_STATE.md](PROJECT_STATE.md) (newest entry on top) covering: what was implemented, key decisions made, what's still open, and known bugs/next steps. `PROJECT_STATE.md` is the running progress log — `CLAUDE.md` stays reserved for durable project rules and technical notes and should not accumulate changelog entries.

After each meaningful milestone, create a git commit.
